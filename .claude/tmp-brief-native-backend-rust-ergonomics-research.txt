# native-backend-rust-ergonomics-research

Maintainer note (composed 2026-09-04): investigate whether the native/LLVM backend is properly
ergonomic today, in the sense that we should be using well-established Rust libraries for this
rather than hand-writing everything in raw LLVM IR/C -- ideally gaining the ability to write
integrated code directly in Rust, or even import functionality from other crates, instead of
manually authoring it in runtime/toylang.c or src/emit_llvm.rs.

Investigate:
1. Survey what an inkwell-based (or similar) LLVM codegen layer would buy in ergonomics and
   correctness versus the current hand-written approach in src/emit_llvm.rs, and what it would
   cost in build complexity/toolchain deps.
2. Survey what a thin Rust runtime crate (in place of hand-rolled C in runtime/toylang.c) would
   buy, and what it would cost.
3. Ground the survey in concrete recent evidence: the issue-177 lane (sort_by/max_by) spent much
   of a 193-step run hand-patching runtime/toylang.c with oldString-not-found edit failures and a
   self-introduced combining-character corruption bug while adding four keyed C helper functions
   -- exactly the kind of hand-authored-C friction this note is asking about. Look at that lane's
   history/diffs if still available, or reason from the pattern described.
4. Produce concrete code comparisons: e.g. take one or two real helper functions currently in
   runtime/toylang.c or a recent codegen addition to src/emit_llvm.rs, and show what the
   equivalent would look like written against inkwell / as a Rust runtime function instead.

This is a research spike, not an implementation: do not migrate any real backend code. Write
findings (with the concrete code comparisons) to plans/, then compose a design round.
