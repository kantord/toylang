# vec-as-dataframe-type-research

Research spike spun off dense-tensor-type round 5 (maintainer freeText, 2026-09-02). Source of
truth: plans/dense-tensor-design-research.md (sensor-pipeline example) and the round 5 answer
recorded in plans/board.yaml under dense-tensor-type.

The maintainer's lean: not a new flat-buffer tensor value kind, but treating Vec itself as
inherently the dataframe/tensor-capable type -- a bare-minimum set of dataframe primitives
(reshape, transpose, broadcast, reduce) implemented over the existing simple Vec<Vec<Num>> layout.

Investigate:
1. Whether that needs an explicit type-design change (formally making Vec a multi-dimensional
   type), or can be built as stdlib primitives over the current simple Vec<Vec<Num>> type
   unchanged.
2. Run both approaches against the sensor-pipeline example from
   plans/dense-tensor-design-research.md and compare.
3. Note the transpose sub-question left open by round 5: single tensor(n;m) constructor+transpose
   vs a generalized multi-dimensional transpose.

This is a research spike, not an implementation: write findings (with concrete toylang code
comparisons) to plans/, then compose a design/decide round grounded in the maintainer's actual
framing rather than re-presenting the old A/B/C options. Do not implement the primitives yet --
that's for a follow-up build row once the design round settles the shape.
