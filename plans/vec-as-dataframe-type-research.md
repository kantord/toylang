# Vec as the dataframe type: stdlib primitives over `Vec<Vec<Num>>`, or a type-design change

Groundwork for the next [dense-tensor-type re-ask](dense-tensor-design-research.md). Round 5's C ruling deferred the flat-buffer value kind; the maintainer's freeText leans further: no new kind at all,but treating `Vec` itself as the dataframe/tensor-capable type,with a bare-minimum set of dataframe primitives (reshape, transpose, broadcast, reduce) over the existing `Vec<Vec<Num>>` layout. This spike runs this framing against the sensor pipeline the dense doc already worked out,to ground whetherthe primitives need an explicit type-design change or ride the current simple type unchanged. The pipeline's shape here is 2x3 rather than the dense doc's 3x1024 (the numbers are not the point);the stages are the same.

Two language facts bound everything below. Q2 is open:an operator over a `Vec` is refused for every op except `+`,which concatenates two `Vec`s of the same element type (the Q2 guard at [check/mod.rs:3173](https://github.com/kantord/toylang/blob/main/src/check/mod.rs#L3173),andthe add-trait ruling,[kantord/toylang#97](https://github.com/kantord/toylang/issues/97)). A comparison on any type carrying a `Vec` is refused for the same reason (`contains_vec`,[ty.rs:246](https://github.com/kantord/toylang/blob/main/src/ty.rs#L246)). There is no generic `fold` builtin:`sum` and `max` arethe only reductions,both type-restricted to `Int`/`Int64` ([tir.rs:267](https://github.com/kantord/toylang/blob/main/src/tir.rs#L267)). And `Float` does not exist yet (`@f32` fromthe dense pipeline presupposes it),so every repro below uses `Int` in its place.
