Board row `seq-type-primitive-build`. Give `Seq` its own `TypeExpr` variant, parser rule, and
checker treatment, matching ADR 0008's `Seq<T, Stream<T>>` / `Seq<Star<T>, E>` notation
(docs/adr/0008-stream-protocols-are-kleene-patterns.md) so the sequence-pattern algebra the ADR

checker + a corpus test. Emitting a runtime pair for a `Seq` value is a follow-up row -- do not
build backend emission in this row.

Read docs/adr/0008-stream-protocols-are-kleene-patterns.md in full first. Key facts from it:
- `Seq<Head, Rest>` is a two-argument type constructor -- head-plus-remainder, e.g.
  `Seq<T, Stream<T>>` (a provably nonempty stream) or `Seq<Star<T>, E>` (a stream with a typed
  closing message). This is UNLIKE `Vec<T>`/`Stream<T>`, which each take exactly one type
  argument -- `Seq` takes two.
- `Star<T>` is `Stream<T>` under a different name in this algebra -- check with the maintainer's
  ADR text whether `Star` is a spelling alias for `Stream` (likely: `Star<T>` in Kleene-algebra
  terms IS `Stream<T>`, so no new `Star` constructor is needed -- reuse `TypeExpr::Stream`/
  `Type::Stream` for it). Confirm this reading against the ADR before writing code; if the ADR
  text is ambiguous about whether `Star` needs its own name or is purely notation for `Stream`,
  pick the reading that reuses `Stream` (simpler) and say so explicitly in your summary.
- Soundness condition from the ADR: `Stream` (and by extension any pattern containing one, i.e.
  a `Seq` whose head or rest is/contains a `Stream`) never appears under a value constructor
  (not inside a Vec, a record, another Stream, or -- by the same rule -- stored as a plain
  value) and may appear freely under pattern constructors. `Seq` should inherit `Stream`'s
  existing position restrictions wherever a `Seq` transitively contains a `Stream`, the same way
  `Type::Stream` is already restricted (see below).
