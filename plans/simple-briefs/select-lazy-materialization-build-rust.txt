## What exists today (eager, what you're replacing)

Rust has no standalone `tl_select` helper -- unlike JS/Go, `Select` is emitted fully inline as an
iterator chain at the `Kind::Select` match arm, `src/emit_rs.rs:1597-1606`:

```rust
// `.cloned()` before `.filter()` keeps the closure's parameter at exactly one level
// of reference (`&T`, not `&&T` the way `.iter().filter()` alone would give):
// `.clone()` on `&T` derefs one level to `T`, but on `&&T` it only strips one level
// of reference, leaving `&T` -- verified directly, not assumed.
Kind::Select {
    source,
    param,
    pred,
} => format!(
    "{}.iter().cloned().filter(|{}: &{}| -> bool {{ {} }}).collect::<Vec<_>>()",
    self.expr(source),
    self.local(*param),
    self.rs_type(tir::runtime_elem(&source.ty).expect("select runs over a dimension")),
    self.expr(pred)
),
```

`.filter().collect()` walks the source once and eagerly allocates a new, shorter `Vec` before
anyone asks for an element.

## What to build instead

Replace the eager `.filter().collect()` with a lazily-built selection: build a mask/selection-
vector once (O(n) over the mask bits), then give O(1) indexed access into it without copying the
filtered elements out yet. Compact (materialize a real `Vec`) only on the first strong
(non-transient) reference -- reusing the source's underlying allocation in place if the source is
uniquely referenced at that point, copying otherwise. This mirrors the same provably-one-reference
condition `mutation-semantics-spike` (`plans/mutation-semantics-spike.md`, "(2) Is the rule
decidable from the current TIR?") already established for fused-loop/copy-elision: a name with
exactly one use, that use consuming, no use following it -- decidable from a TIR occurrence-count
scope walk, no borrow checker, no runtime refcounting.

Do NOT change `Kind::Select`'s AST/checker shape or its observable semantics -- `xs | select(pred)`
must keep producing the exact same elements in the exact same order as today. This is purely a
change to how the Rust backend *represents* the result between the `select` call and whatever
consumes it next (indexing, iteration, another pipe stage, etc.).

Since Rust currently has no standalone select helper to modify, this likely means introducing one
(a real function, not inline codegen) and registering it in the conditional-inclusion table the
same way every other builtin helper is: see `MAX_BY_HELPER` for both the helper-const style
(`src/emit_rs.rs:232-238`) and its registration:

```rust
// helper const, src/emit_rs.rs:232
const MAX_BY_HELPER: &str = r#"fn tl_max_by<T: Clone, K: Ord>(v: &[T], key: impl Fn(&T) -> K) -> Option<T> {
    let mut m = v.first()?;
    for x in &v[1..] {
        if key(x) > key(m) {
            m = x;
        }
    }
    Some(m.clone())
}
"#;
```
