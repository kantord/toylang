## Design to build (mirrors the already-proven Go version; translate the shape, not the syntax)

Make `tl_select` return a lazy handle instead of a plain array; build the selection vector once,
on first use; give O(1) indexed access without copying survivors out. Any consumer that isn't
plain indexing just densifies first (always correct, just not lazy for that path):

```js
function tl_sel_new(src, pred) {
  return { __tlSel: true, src, pred, idx: null, dense: null };
}
function tl_sel_build(s) {
  if (s.idx !== null) return;
  const idx = [];
  for (let i = 0; i < s.src.length; i++) if (s.pred(s.src[i])) idx.push(i);
  s.idx = idx;
}
function tl_sel_dense(s) {
  if (s.dense !== null) return s.dense;
  tl_sel_build(s);
  s.dense = s.idx.map((i) => s.src[i]);
  return s.dense;
}
```

Then make `tl_at` and `tl_slice` polymorphic: if `v && v.__tlSel`, either answer directly from the
selection vector (the actual laziness win, for `tl_at` at `depth === 0`: `tl_sel_build(v)`, apply
the same negative-index/bounds logic against `v.idx.length`, return `{some: v.src[v.idx[i]]}` or
`"none"`) or fall back to `tl_sel_dense(v)` then proceed with the existing plain-array logic
unchanged (simplest correct option for `tl_slice` and the `depth > 0` recursive case in both
helpers). Do the same densify-at-the-boundary check for any other consumer you find per the list
above.

The in-place/reuse optimization (reusing the source's backing array when uniquely referenced) that
the shared spec mentions is a perf nicety, not required for this row's done-gate -- skip it; a
version that always copies on `tl_sel_dense` is correct and acceptable.
