Today, `tl_select` walks the source once and eagerly builds a new, shorter array before anyone
asks for an element.

## What to build instead

Replace the eager filter with a lazily-built selection: build a mask/selection-vector once (O(n)
over the mask bits), then give O(1) indexed access into it without copying the filtered elements
out yet. Compact (materialize a real array) only on the first strong (non-transient) reference --
reusing the source's underlying array in place if the source is uniquely referenced at that point,
copying otherwise. This mirrors the same provably-one-reference condition
`mutation-semantics-spike` (`plans/mutation-semantics-spike.md`, "(2) Is the rule decidable from
the current TIR?") already established for fused-loop/copy-elision: a name with exactly one use,
that use consuming, no use following it -- decidable from a TIR occurrence-count scope walk, no
borrow checker, no runtime refcounting.

Do NOT change `Kind::Select`'s AST/checker shape or its observable semantics -- `xs | select(pred)`
must keep producing the exact same elements in the exact same order as today. This is purely a
change to how the JS backend *represents* the result between the `select` call and whatever
consumes it next (indexing, iteration, another pipe stage, etc.).

Per-backend builtin-wiring precedent to follow (naming/registration convention):
`src/emit_js.rs:230` (`SUM_HELPER`, registered the same way `SELECT_HELPER` is, at
`src/emit_js.rs:295`).
