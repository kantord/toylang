## Checker contract already in place (read-only, do not change)

`src/check/mod.rs`'s `transpose_call`: refuses non-`Vec<Vec<Int|Int64>>` input at COMPILE time
(`` `transpose` needs a Vec of Vecs of Int or Int64, found {ty} ``) -- so "non-numeric input" is
already a checker-level refusal, not something backends need to guard. Raggedness (rows of
unequal length) is NOT statically checked -- `Vec<Vec<T>>` doesn't carry per-row length in the
type -- so every backend needs its own RUNTIME check, refusing ragged input the same way Go/Rust
already do (`tlFail`/`tl_fail("transpose needs a rectangular Vec of Vecs")`, see
`src/emit_go.rs:245-260` / the analogous Rust helper). Cross-backend agreement means a ragged input
must be refused identically on all 7 backends, not silently produce garbage on some.

## JS -- `src/emit_js.rs` (mirror `MAX_HELPER`'s registration exactly)

```js
// `vv[r][c]` becomes `out[c][r]`; every row has `vv[0].length` cells because the checker
// refuses a ragged literal, and a zero-row or zero-column matrix transposes to the empty one.
function tl_transpose(vv) {
  if (vv.length === 0) return [];
  for (const row of vv) {
    if (row.length !== vv[0].length) throw new Error("transpose needs a rectangular Vec of Vecs");
  }
  const out = [];
  for (let c = 0; c < vv[0].length; c++) {
    const row = [];
    for (let r = 0; r < vv.length; r++) row.push(vv[r][c]);
    out.push(row);
  }
  return out;
}
```
Register a `used.transpose` flag (follow `used.max` exactly) in the `Helpers` struct, the
`walk()` pass, and the helper-emission list; wire `Builtin::Transpose => format!("tl_transpose({})", expr(enums, arg))`
in the `expr()` match, alongside `Builtin::Max`.

## Python -- `src/emit_py.rs` (mirror `MAX_HELPER`'s registration exactly)

```python
def tl_transpose(vv):
    if len(vv) == 0:
        return []
    ncols = len(vv[0])
    for row in vv:
        if len(row) != ncols:
            raise Exception("transpose needs a rectangular Vec of Vecs")
    return [[vv[r][c] for r in range(len(vv))] for c in range(ncols)]
```

## Lua -- `src/emit_lua.rs` (mirror `MAX_HELPER`'s registration exactly)

```lua
local function tl_transpose(vv)
  if #vv == 0 then return {} end
  for r = 1, #vv do
    if #vv[r] ~= #vv[1] then error("transpose needs a rectangular Vec of Vecs") end
  end
  local out = {}
  for c = 1, #vv[1] do
    local row = {}
    for r = 1, #vv do
      row[r] = vv[r][c]
    end
    out[c] = row
  end
  return out
end
```

## LLVM -- `src/emit_llvm.rs` + `runtime/toylang.c` (this is the one with no crib code -- new
## runtime function required, follow `tl_vec_flatten`'s pattern for handling a Vec of Vecs)

The LLVM backend calls into a C runtime (`runtime/toylang.c`) rather than emitting inline logic.
`tl_vec_flatten` (`runtime/toylang.c:1331-1348`) is the closest existing precedent for operating on
a `Vec<Vec<T>>`: the outer `tl_vec`'s single column (`cols[0]`) holds one `tl_vec*` pointer per
row. Add, near `tl_vec_max`/`tl_vec_flatten`:

```c
/* `vv[r][c]` becomes `out[c][r]`; ragged input (rows of unequal length) is refused at runtime
 * since Vec<Vec<T>> carries no per-row length in its type. */
tl_vec *tl_vec_transpose(const tl_vec *vv) {
    if (vv->len == 0) {
        return tl_vec_new(0, 1);
    }
    const tl_vec *row0 = (const tl_vec *)vv->cols[0][0];
    int64_t ncols = row0->len;
    for (int64_t i = 0; i < vv->len; i++) {
        const tl_vec *row = (const tl_vec *)vv->cols[0][i];
        if (row->len != ncols) {
            const char *msg = "toylang: transpose needs a rectangular Vec of Vecs\n";
            (void)!write(2, msg, strlen(msg));
            exit(1);
        }
    }
    tl_vec *out = tl_vec_new(ncols, 1);
    for (int64_t c = 0; c < ncols; c++) {
        tl_vec *newrow = tl_vec_new(vv->len, 1);
        for (int64_t r = 0; r < vv->len; r++) {
            const tl_vec *row = (const tl_vec *)vv->cols[0][r];
            newrow->cols[0][r] = row->cols[0][c];
        }
        out->cols[0][c] = (int64_t)newrow;
    }
    return out;
}
```
(Follow `tl_div_by_zero`'s write(2, ...)+exit(1) pattern for the runtime error, as shown -- that's
this codebase's existing convention for a hard runtime refusal, not an exception mechanism.)
