-- split from `dense-tensor-type-build` per maintainer ruling (wizard submission,
stuck-cross-backend-scope-escalation round, 2026-09-13, option A). `tensor-transpose-build`, the
easier sibling half of that split, has already landed on main (commits baa3d76/3aa7d7f/1e023f2)
using the plain unary-`Builtin` pattern -- do not copy its approach uncritically, because THIS row
is the harder half specifically because `tensor(n; m)` needs a call form the parser does not have

made zero edits getting stuck here, which is why this was split out on its own. This brief exists
to unblock exactly that stuck point.

## What's new: parsing `f(a; b)`

Every call in this language today takes at most ONE argument -- `Expr::Call { func, arg:
Option<Box<Expr>>, .. }` in `src/ast.rs`, parsed in `src/parse.rs` around line 1635-1669 (the
function handling a bare identifier followed by `(`). There is no comma- or semicolon-separated
multi-arg call anywhere in the grammar. However the LEXER already tokenizes `;` as `Tok::Semicolon`
(`src/parse.rs:84,135,226`) -- it's just never consumed by the parser, so `tensor(n; m)` is
currently a parse error.

The codebase's existing pattern for a new call *shape* is a dedicated `Expr` variant, not a
generalized N-ary `Call` -- see `Expr::ColonCall` (`src/ast.rs:429`, `receiver:method(arg)`) and
`Expr::Variant`/`match_call` (capitalized-name calls, `src/parse.rs:1614-1622`), both special-cased
by name/shape in the same function that parses `Call`. Follow that precedent instead of widening
`Expr::Call` itself (which would ripple into the checker and all 7 backends for every existing
call site, not just this one):

1. Add `Expr::TensorNew { rows: Box<Expr>, cols: Box<Expr>, span: Span }` to `src/ast.rs` (near
   `ColonCall`), plus its `span()` match arm (`src/ast.rs:572-581` shows where existing variants
   are listed).
2. In `src/parse.rs`'s call-parsing function, before the generic `if next == Tok::LParen` handling
   at line 1641, special-case `name == "tensor"`: consume `(`, parse an expr, `self.eat(Tok::
   Semicolon)`, parse a second expr, `self.eat(Tok::RParen)`, produce `Expr::TensorNew`. Mirror
   `colon_call` (`src/parse.rs:1556`) for the shape of a small dedicated parse helper.
3. Register `"tensor"` wherever a callable name needs to be recognized as one before this dispatch
   fires -- `bare_callee` (`src/parse.rs:1784`) and `takes_argument` (`src/parse.rs:627`) gate
   whether a name is treated as a call at all; check both for whether `tensor` needs adding, the
   same way every other builtin name already does.

## Lowering and checking

`src/tir.rs` has no unary-only restriction -- `Kind::Arith { op, lhs: Box<Tir>, rhs: Box<Tir> }`
and `Kind::Concat(Box<Tir>, Box<Tir>)` (`src/tir.rs:81-90`) are the existing two-operand precedent.
Add a `Kind::TensorNew { rows: Box<Tir>, cols: Box<Tir>, data: Box<Tir> }` (or fold rows/cols into
a single `Builtin`-style tag if that fits the existing `Builtin` enum better once you're looking at
it -- `Builtin::Transpose` is at `src/tir.rs:282`, tagged in `src/tags.rs:191`, dispatched in
`build.rs:193`, checked in `src/check/mod.rs:3780`; use that four-file fan-out as your checklist
for wiring the new node through, adjusted for the extra operand).

Checker ruling to implement (`dense-tensor-type` design, `plans/dense-tensor-design-research.md`
has the full trail):
- No separate `Tensor` value kind -- lower to the existing `Vec<Vec<T>>` type (`src/ty.rs`), not a
  new `Type::Tensor` variant.
- `tensor(n; m)` takes a flat or nested numeric input, reshapes it into `n` rows of `m` elements
  each, one call, one failure point.
- Hard-fail (compile-time where the shape is known, else a runtime refusal matching the posture of
  `contains_vec`-gated refusals already in `src/check/mod.rs`) on: a null element, a ragged input,
  a non-numeric element, or an input whose length doesn't equal `n * m`. No validity bitmask --
  this is a deliberate, previously-flagged-tentative pick; do not build one.

## Per-backend wiring

Once the checker/TIR node exists, wire `TensorNew`/whatever you named it into all 7 backends
(`src/emit_go.rs`, `src/emit_js.rs`, `src/emit_py.rs`, `src/emit_lua.rs`, `src/emit_rs.rs`,
`src/emit_jq.rs`, `src/emit_llvm.rs`) the same way `Builtin::Transpose`'s call sites in each of
those files already show for a builtin taking a `Vec` and producing a `Vec<Vec<T>>` -- the shape
differs (two extra scalar operands `n`/`m` instead of zero) but the seven-file fan-out and the
runtime-refusal-on-bad-shape pattern are identical to what's already landed for transpose.

Done-gate: a real `.toy` program builds a tensor via `tensor(n; m)` from row-major flat input (e.g.
`[1,2,3,4,5,6] | tensor(2; 3)` yielding `[[1,2,3],[4,5,6]]`), and a downstream reduction over it
(e.g. `| map(sum(.))`) produces identical output across all 7 backends (the existing
corpus-conformance harness in `just check` is the check). A program that calls `tensor(n; m)` with
a null, ragged, non-numeric, or wrong-length input is refused identically on every backend, not
just some -- same standard the landed `transpose` already meets.
